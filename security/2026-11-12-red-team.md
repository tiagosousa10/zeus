# Auditoria Zeus — code review e red team — 2026-11-12

> Relatório histórico anterior às correções. Estado atualizado e evidências: [remediação](2026-11-12-remediation.md).

Âmbito: árvore completa e histórico git; web, desktop, API, frontend, backend, persistência, arquitetura e entrega. Commit inicial: `4b6d15b4abe3bdcfd99a5ed7139b9ac47a5bf947`. Árvore inicialmente limpa. **Durante o fecho foi criado externamente o commit `542368f`, reorganizando o desktop para apps/desktop/**; os caminhos/linhas deste relatório referem-se ao snapshot inicial, salvo indicação. A auditoria não realizou nem reverteu essa reorganização; o delta recebeu leitura complementar e novo typecheck.

Segurança: **0 críticos, 0 altos, 5 médios confirmados**. Code review: **2 heurísticas Standards e 1 bug Spec**. Não foi demonstrado RCE, bypass inicial de autenticação ou acesso entre Membros. Estes resultados não são garantia de ausência de outras vulnerabilidades.

## Sumário executivo

Os principais problemas atingem disponibilidade: um XMLTV hostil pode bloquear o event loop da API, pedidos simultâneos criam processos FFmpeg sem teto e a cache IPTV cresce indefinidamente no disco. O reset de password não revoga sessões anteriores, prolongando acesso caso um cookie já tenha sido roubado. A configuração PostgreSQL antiga permite acesso por outras contas locais se o contentor legado estiver ligado com a password predefinida. Separadamente, a recuperação de password por email está funcionalmente bloqueada para pessoas sem sessão. Guards de Membro/TOTP, ownership, token do motor e proteção SSRF estão presentes nos caminhos inspecionados.

A revisão não alterou código, não iniciou a aplicação nem contactou fornecedores, bases reais ou instalações Zeus. Foram usados scanners locais e fontes públicas de advisories/código de dependências. As seis skills especialistas foram explicitamente confirmadas pelo utilizador.

## Achados de segurança

### R-001 — [INJECTION: médio] XMLTV malformado bloqueia o event loop

- **CWE:** CWE-1333 / CWE-400 · **OWASP:** A03 · **Confiança:** 10/10 · **Esforço:** M.
- **Local:** `apps/api/src/modules/iptv/epg.ts:45`, `:69`; entrada `apps/api/src/modules/iptv/epg-routes.ts:69`.
- **Cadeia:** fornecedor controla XMLTV, ou Membro configura epgUrl próprio → fetch admite até 160 MiB e apenas verifica presença de `<tv>` → sequência de aberturas programme sem fechos força rescans quadráticos da regex síncrona → API inteira deixa de responder. Filtro temporal ocorre depois do match; timeout de rede não interrompe CPU síncrona.
- **Raio:** todos os Membros da instalação e desktop dependente da API. Não requer acesso anónimo à API; um fornecedor comprometido pode desencadear o problema durante leitura legítima.
- **Repro seguro:** benchmark isolado pequeno descrito acima, sem descarregar XMLTV externo.
- **Correção:** parser incremental com orçamento de bytes/eventos/profundidade, rejeição linear de estrutura incompleta e worker terminável com orçamento de tempo. Reduzir apenas o limite de bytes não elimina a classe de problema.
- **Refutação:** independente, CONFIRMADO; datas, timeout e cache não removem o caminho.

### R-002 — [API-SURFACE: médio] Uma sessão permite remux concorrentes sem teto

- **CWE:** CWE-770 · **Confiança:** 10/10 · **Esforço:** M.
- **Local:** `apps/api/src/modules/iptv/play-routes.ts:442`, `:463`, `:481`; `apps/api/src/modules/iptv/remux.ts:83`.
- **Cadeia:** Membro verificado obtém sessão para conteúdo elegível → mantém vários GET remux.mp4 do mesmo token → cada pedido cria bridge e FFmpeg → consumo de CPU/memória/sockets e ligações ao fornecedor.
- **Raio:** recursos do Mac e disponibilidade da instalação. Uma sessão por lista limita tokens, não os leitores de um token.
- **Repro seguro:** teste conceptual com dois pedidos e spawn simulado; contar duas criações. Não se executou carga real.
- **Correção:** um remux ativo por sessão, cancelamento/substituição explícitos e limite global/per-Membro; 409/429 quando ocupado. Cleanup ao cancelar não substitui controlo de admissão.
- **Refutação:** independente, CONFIRMADO; expiração e cancelamento não limitam concorrência.

### R-003 — [DATA-MODEL: médio] Cache persistente acumula ficheiros sem quota

- **CWE:** CWE-770 · **Confiança:** 9/10 · **Esforço:** M.
- **Local:** `apps/api/src/modules/iptv/cache.ts:48`, `:69`, `:97`; `apps/api/src/modules/member/routes.ts:41`.
- **Cadeia:** Membro muda repetidamente list.id via PATCH state → consulta catálogo de cada ID → ID integra hash da cache → novo ficheiro .bin persistido → ficheiros antigos nunca são recolhidos, mesmo expirados/removidos → esgotamento gradual do volume.
- **Raio:** disco que contém perfil e SQLite; afeta toda a instalação. O máximo de 100 listas simultâneas não limita IDs históricos; o orçamento RAM não limita disco.
- **Repro seguro:** conceptual, dois IDs para a mesma lista criam duas entradas; avanço de relógio/remoção da lista não as elimina. Não se encheu disco.
- **Correção:** quotas global/per-Membro em bytes e entradas, recolha TTL/LRU e invalidação ao eliminar listas; preservar escrita atómica.
- **Refutação:** independente, CONFIRMADO; unlink existente remove apenas temporários falhados.

### R-004 — [IDENTITY: médio] Reset mantém sessões anteriormente comprometidas

- **CWE:** CWE-613 · **Confiança:** 10/10 · **Esforço:** S.
- **Local:** `apps/api/src/modules/auth/service.ts:21`; `apps/api/src/modules/auth/middleware.ts:6`.
- **Cadeia:** atacante já possui cookie de sessão TOTP verificada → titular repõe password → configuração não ativa revokeSessionsOnPasswordReset → sessão e verified_session sobrevivem → cookie antigo continua autorizado até expiração/revogação.
- **Raio:** conta já comprometida. Não obtém cookie inicialmente nem contorna TOTP por si só.
- **Repro seguro:** conceptual, duas sessões de teste; após reset confirmar que cookie anterior deveria receber 401. Sem email real enviado. S-001 bloqueia o link anónimo normal, mas o endpoint POST reset continua permitido e não revoga sessões quando usado com token válido.
- **Correção:** `emailAndPassword.revokeSessionsOnPasswordReset: true`; testar eliminação das sessões e cascata de verified_session.
- **Refutação:** independente, CONFIRMADO contra pacote oficial exato 1.7.21: password.mjs só chama deleteUserSessions quando a opção é truthy. [Artefacto oficial consultado](https://registry.npmjs.org/better-auth/-/better-auth-1.7.21.tgz).

### R-005 — [CLOUD/LEGADO: médio] Password fixa permite acesso local ao PostgreSQL antigo

- **CWE:** CWE-798 · **Confiança:** 9/10 · **Esforço:** S.
- **Local:** `compose.yaml:9`; `scripts/migrate-postgres.mts:14`.
- **Cadeia:** outra conta/processo local → TCP 127.0.0.1:55439 → credencial predefinida versionada → leitura/escrita da base legada, incluindo alteração de contas/sessões antes da migração.
- **Condições:** contentor legado ligado e credencial predefinida ainda vigente. **Não afeta instalação nova apenas SQLite.** Não foi verificado se há contentor ligado ou credencial válida numa instalação real.
- **Raio:** dados/contas legados e integridade da importação; blobs cifrados ainda exigem chaves. Loopback restringe hosts remotos, não outras contas locais.
- **Repro seguro:** conceptual, segunda conta num ambiente descartável com dados fictícios e SELECT current_user; nenhuma base real consultada.
- **Correção:** remover password/fallback literais, exigir segredo próprio e URL explícito. Rodar password dentro de volumes existentes; alterar variável Compose não roda uma password já inicializada. Encerrar contentor após migração validada.
- **Refutação:** independente, CONFIRMADO condicionalmente; password já alterada ou contentor desligado impedem exploração nessa instalação.

## Spec

### S-001 — Recuperação de password por email exige sessão existente (P1)

Requisito: README.md:32 anuncia «recuperação de password»; spec aprovada exige «Implementar ecrãs reais [...] com estados vazios/erro honestos» em `docs/superpowers/specs/2026-11-11-zeus-approved.md:17`.

`apps/api/src/modules/auth/routes.ts:96–109` permite apenas `/reset-password`, mas `service.ts:28` envia o callback `/reset-password/<token>`. Um clique sem sessão cai no guard e recebe 401 antes de Better Auth validar o token/redirecionar para o formulário. `Entry.tsx:209` fornece redirectTo correto.

Confirmado por dois revisores contra o código oficial **1.7.21**, incluindo construção do URL e definição GET `/reset-password/:token`. [Fonte oficial versionada](https://github.com/better-auth/better-auth/blob/v1.7.21/packages/better-auth/src/api/routes/password.ts#L138).

**Correção:** permitir especificamente o callback GET parametrizado, mantendo validação/expiração/callback em Better Auth. Testar pedido anónimo → email capturado localmente → clique → formulário → reset. Confiança 10/10; não foi enviado email nem executado fluxo contra instalação real.

SQLite, pesquisa global, controlos do leitor e composição dos heros foram tratados segundo decisões posteriores autorizadas. Sem scope creep confirmado; fidelidade visual não validada dinamicamente. **Total Spec: 1 achado; maior impacto neste eixo: recuperação indisponível sem sessão.**
